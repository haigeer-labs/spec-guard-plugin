# 审查透镜

> 这个仓库从 0.1 到 0.7.8 修过的东西里，**大部分不是新 bug，是同几种错反复换个位置发生**。
> 这份文档把那几种错固定成透镜：改完一处，对着它们各照一遍。
>
> 每条都带**出处版本**。没有出处的条目不该出现在这里 —— 方法论最容易的堕落
> 就是事后编因果。

---

## A. 关于判据（你写的检查器、测试、门禁）

### A1. 假断链比不报断链危害大得多

**这是本仓三条不可违反的性质之一，也是被违反次数最多的一条。**

| 版本 | 谁被误报了 |
|---|---|
| 0.5.0 | 已归档的 `todo.md` 被当成活清单 |
| 0.5.1 | 项目处在两个 initiative 之间（刻意空闲）被当成断链 |
| 0.6.0 | 模块分支 `feat/<module-id>` 不含 issue 号 → 每轮报「在错误分支上工作」 |
| 0.7.11 | 模块 id 自带数字（`feat/oauth2`）→ `2` 被当成 task issue 号（verify-artifacts） |
| 0.7.12 | 同上，phase-guard 那一边（**每轮都跑**）；以及本地模式够不到「刻意空闲」豁免 |

**怎么用**：加任何一条 `broken()` 之前问「这个状态有没有**正常**的成因」。
想不出来不等于没有 —— 0.5.1 那次就是想不出来。

### A2. 防线本身也要被测试

新写的检查器**默认是坏的**，直到你用真实数据跑过一遍。

| 版本 | 防线自己的毛病 |
|---|---|
| 0.5.2 | `check-command-names` 漏了双引号前缀，抓不到 `NEXT="/plan …"` —— 也就抓不到它本该抓的那个 bug |
| 0.7.1 | `check-readme-sync` 第一版没跑反向用例 |
| 0.7.2→0.7.3 之间 | 发版 sha 核对拿 `HEAD` 比，只改文档的提交就误报（未记入 CHANGELOG，见 commit `138d5c3`；它修的是同一段里 `b5cf739` 刚写下的办法） |
| 0.7.4 | evals 判分把 skill 名写死成裸名（实际是 `spec-guard:spec-github-bridge`），把一次成功判成失败 |

四次同一个形状：**判据写完没有当场用真实数据跑一遍。**

**怎么用**：`scripts/test-checkers.sh` 里加一正一反。
「反」是重点 —— **一个永远返回 0 的校验器和没有校验器没区别**。

### A2b. 写下来的规则拦不住任何东西，检查器才能

规则**已经写在显眼处**，然后照样被违反：

| 规则写在哪 | 违反了几次 |
|---|---|
| CLAUDE.md 的「禁止」清单：不要写 `cmd \| grep -q` | 3 次（gh `--help` / `find todo.md` / `is_archived`），每次都是修一处漏一处 |
| `verify-artifacts.sh` 顶部：「重叠项的判定规则必须两边一致」 | 写下它的那次提交（0.7.11）自己就只改了一边 |
| `verify-artifacts.sh:122` 行内：「herestring：管道 + grep -q 会 SIGPIPE」 | 同一个文件里隔 80 行的 `is_archived` 就是那个写法 |

注意第二、三条：**规则和违例在同一个文件里，甚至是同一次提交写下的**。
所以这不是「没看见文档」的问题，靠「下次记得」解决不了。

`check-bash32.py` 是这条的正面例子 —— 那条规则同样写在 CLAUDE.md 里，
但它有检查器，所以没有第二次。0.7.12 给 `| grep -q` 补了
`check-grep-pipe.py`。

**怎么用**：发现自己在注释或 CLAUDE.md 里写「必须 / 不要 / 两边要一致」时，
问一句「**这条能不能变成一个 `check-*.py` 或一条断言**」。
能就去写；不能就承认它只是提示，别指望它生效。

**能变成检查器时，优先问被判的那个东西本人，而不是冻结一份清单。**
0.7.14 的 `check-gh-json-fields.py` 判的是「文档里写的 `gh … --json <字段>`
存不存在」——它不维护字段表，而是跑 `gh issue view 1 --json <乱写>`
让 gh 自己吐出合法字段（这一步 gh 在**本地**做，不需要仓库、网络或登录）。
冻结清单的版本今天也能抓到 `dependencies`，但 gh 明年加一个字段它就开始误报，
而误报会让人把整个检查关掉（见 A1）。
问不到就**干净跳过并声明「跳过不代表通过」**，不假阻塞。

### A3. 判据管得太宽和管得太窄一样是缺陷

两个方向都出过：

- **太宽**（0.7.3）：`check-command-names` 把测试里构造的假路径
  `CLAUDE_PLUGIN_ROOT=/x/spec-guard/9.9.9` 当成斜杠命令 `/x`，把 `validate` 判红。
  它的自我定位是「**会到达用户眼前**的输出」，回归测试不在其中 → 收窄。
- **太窄**（0.7.4）：`check-bash32` 抓到测试脚本自己（构造坏样本时源码必然含那个模式）。
  这次**没有**用「跳过 `test-*.sh`」的豁免，而是把坏样本改成运行时拼装 ——
  放宽会削掉真实覆盖：测试脚本自己也得能在 bash 3.2 上跑。

**怎么用**：判据报错时，先问「它的自我定位是什么」，再决定收窄还是让被测方让路。
**豁免也是行为，加了就要有用例**（0.7.4 给 0.7.3 那条豁免补了正反用例，
否则下次收紧范围会静默把它去掉）。

### A4. 失败必须可观察

| 版本 | 静默在哪 |
|---|---|
| 0.2.1 | macOS bash 3.2 上 `$VAR` 紧跟全角括号 → hook 崩溃，而 hook 失败是静默的 |
| 0.4.1 | `gh issue list --parent` 这个 flag 不存在 → 每次失败、静默落进降级分支，**GitHub 层从没真正跑过** |
| 0.7.8 | `hooks.json` 结尾 `|| true` 吞掉非零退出；`emit()` 可能吐半截 JSON，宿主拒绝也是静默的 |

原话（0.4.1）：**一个永远在降级的探测器，和一个坏掉的探测器没有区别。**
0.7.8 补上另一半：**崩掉的比降级的更隐蔽，因为降级至少还有文案。**

**怎么用**：写完兜底分支，问「掉进这里的时候，看得出来吗」。
「什么都不输出」几乎永远是错的默认值。

## B. 关于验证

### B1. 在一个配置下验证，全局发货

| 版本 | 只验了什么 / 漏了什么 |
|---|---|
| 0.7.4 | 0.7.0 同时改了两个 hook 的激活判据，只给 `phase-guard` 加了测试，`verify-artifacts` 漏了三个版本 |
| 0.7.11 | 0.6.0 改模块分支约定时只改了 `phase-guard`。当时 grep 找的是 `BRANCH`，而 `verify-artifacts` 里那段叫 `BR`/`BRI` —— **一次失败的搜索被当成了「这里没有」**，于是它在 task 分支时代留了五个版本 |
| 0.7.6 | 0.7.5 的零足迹注入只在 github 模式下验过，本地模式被指向一个全篇讲 GitHub 的 skill |
| 0.7.7 | 声明 `gitlab`/`jira` 的项目从没走过自己的分支，一路掉进为 GitHub 写的兜底 |
| 0.7.9 | 0.7.0 给 hook 加了第二个激活信号（`state.json`），**没回头检查依赖「激活」这个概念的其他东西** —— `/teardown-convention` 从此移除不干净，删完声明块只是把项目切成零足迹模式 |

**怎么用**：列出**我们发的所有配置**，逐个问「这个改动在它身上是什么表现」。
**「我搜过了，那边没有」不算数** —— 搜不到可能是关键词错了（0.7.11：找 `BRANCH`
而代码里叫 `BR`）。判断某处「不受影响」要靠读，不能只靠一次 grep。
配置之外还有一层容易漏：**改了一个概念的定义（如「什么算激活」），
要把依赖这个概念的所有东西列出来重看** —— 0.7.9 漏的就是 teardown。

**新增一个状态也算改定义。** 0.7.9 引入 `state.json.disabled`，
20 分钟后就发现 `setup-convention` 不认识它 —— 「teardown 后改主意再 setup」
会静默建空 state.json，真映射躺在 `.disabled`，而模型会据此建议 `/sync-map`
去 GitHub 上建一套**重复 issue**（0.7.10）。
**刚发的改动也要过这一遍**，尤其它引入了一个此前不存在的状态。
本仓当前是四种：`github×{有块,零足迹}`、`local×{有块,零足迹(已禁)}`，
外加显式声明的第三方 tracker。

### B1b. 断言的粒度决定它能抓到什么

0.7.12：`test-phase-guard.sh` 的 `chk()` 只比对「阶段名|断链数」，从不看正文。
于是 `有 spec 但没有 tasks//plan.md`（双斜杠是空模块名拼出来的）
和 `/plan 为 [] 拆解任务` 在 52 条断言底下躺了很久 —— 它们的**阶段和断链数
完全正确**，错的全在正文里。

更糟的是那两条断言把畸形输出**锁成了期望值**：修 bug 时它们会红，
读起来像「你改坏了」。

**怎么用**：断言只覆盖它比对的那几个字段。用户看得见正文，就得有断言看正文。

### B2. 对照组有两种，别弄混

- 对照的是**我们也要发的另一个配置** → 它表现差 = **缺陷报告**
  （0.7.5：B 组就是 `--no-claude-md`，「B 没加载 skill」不是佐证 A，是 B 的 bug）
- 对照的是**不装 / 不用**的基线 → 它表现差 = **卖点成立**
  （`evals/module-namespace.sh`：无约定时产物落在 `tasks/plan.md`，正是要治的病）

**怎么用**：设计 A/B 之前先问一句「**B 是不是我们也要发货的东西**」。
分不清的代价 0.7.5 → 0.7.6 已经付过一次。

### B3. 标了「没实测」之后就该去测

0.6.1：「squash 会导致只有最后一个 issue 被关」是从机制推的，
0.6.0 的已知限制里**老实标了「没实测」**，然后就搁在那儿了。
一句 `gh api repos/{owner}/{repo} --jq .squash_merge_commit_message` 就能验，
一验是反的（默认 `COMMIT_MESSAGES` 会拼接 message）。

**怎么用**：「没实测」是**待办**，不是免责。写下它的同时写下验它的那条命令。

### B4. 同一份数据可能回答不止一个问题

0.7.5：`skill-deferral` 首跑的 transcript 早就跑出来了，
当时只读出「声明块起作用了」，没读出「零足迹模式不 work」——
而 B 组恰恰就是零足迹模式。

**怎么用**：得到结论之后，回头问「这份数据还说了什么我没问的」。

## C. 关于改动

### C1. 改约定必须同改状态机和测试，三者是一个原子操作

0.6.0：PR 粒度从 task 提到 module，模块分支按定义不含 issue 号 ——
**新约定的正常状态，就是旧状态机眼里的违规。**

分开做的中间态是「新约定 + 旧检查器」，那个状态下工具在对着正确的行为报错。

### C2. 状态不等于指令

0.7.5：零足迹模式下 hook 正常激活、状态照常注入，**模型全程没加载 skill**。
当时的已知限制写的是「靠 hook 每轮兜底」—— 想当然。
hook 注入的是**状态**，而让 skill 被加载的是那句**指令**。

**怎么用**：**「另一个机制会兜住」是最容易想当然的一类论断** ——
它听起来像系统设计而不像假设，所以不会被当成待验证项。看到这种话就去验。

### C3. 判据会随产品变

0.7.5 修完之后，`skill-deferral` 原来的判据「B 必须不加载」立刻变成错的 ——
**差一点就留下一个断言「零足迹模式必须失效」的评测**。

**怎么用**：改完产品，回头看判据是否还成立。改判据之后拿**旧数据**做反向回归，
确认它还有牙。

---

### C4. 不可逆操作要先钉死「作用于什么」和「做到哪了」

0.7.13 一次查出三处，形状相同：**动手之前没确定作用对象，动手之中没记录进度。**

| 操作 | 缺的是哪一半 | 后果 |
|---|---|---|
| `/setup-convention` | 作用对象 —— 用的是 cwd | 从子目录跑就把 spec/ tasks/ .agent/ 和声明块装进子目录，项目里两套约定，而 hook 只认根上那套 |
| `/teardown-convention` | 同上 | 去删子目录里并不存在的块，报「什么都没做」退 2，根上的约定原封不动 —— **移除报成功却没移除** |
| `/sync-map` | 进度 —— `state.json` 攒到最后一次性写 | 中途失败（限流 / `--type` 被拒 / 用户按停）留下「GitHub 建了一半 + state.json 全空」，而重跑的判据读的正是 state.json → 从头再建一套 Epic 和模块 issue |

两个半边各自都很便宜：作用对象一行
`ROOT="${CLAUDE_PROJECT_DIR:-$(git rev-parse --show-toplevel 2>/dev/null || pwd)}"`；
进度就是「每建成一个立刻写回」而不是「全建完再写」。

**怎么用**：写任何会改外部状态的步骤之前问两句 ——
「**它作用在哪个目录 / 哪个仓库，这件事是被推断的还是被钉死的**」、
「**它做到一半死掉，下次重跑靠什么知道已经做了哪些**」。
第二句尤其容易漏，因为 happy path 上永远看不出区别。

## D. 关于文档与发布

### D1. 两份真相源必然分叉

这是本仓对使用者反复讲的道理，0.7.1 它发生在插件自己身上：
README 把两份模板**逐字内嵌**，从 0.5.x 一路分叉到 0.7.0 ——
而分叉的正是**新用户第一眼会照抄的那段**。

**怎么用**：内嵌不是错，**没有守卫的内嵌才是**（`scripts/check-readme-sync.py`）。

### D2. 已知限制是免检区

0.7.7：「任务层自动化只覆盖 github 和 none」从 0.1 就写着，
于是没人去看那些项目**实际会收到什么** —— 收到的是「恢复 gh」和 `/sync-map`，
两条都是 GitHub 专属建议。

**「不支持」和「给错指引」是两回事：前者是限制，后者是 bug。**

相关的还有 0.7.1：一条**已经不成立**的免责声明（`/deliver` 未实测）挂了三个版本，
劝退使用者用一个已经证明可用的功能。**过期的免责声明比过期文档更糟。**

**怎么用**：定期把已知限制逐条读一遍，每条问两个问题 ——
「它现在还成立吗」「它成立的时候，用户看到的是什么」。

### D3. push 不是发版的终点

0.7.3 前后：连发五个版本之后，本机装着的仍是 **0.5.2** ——
而同一台机器上的目标项目已经跑在新约定上，也就是 C1 说的那个中间态，
在插件作者自己的机器上活了整整五个版本。

**怎么用**：发版流程第 6 步（`CLAUDE.md`），核对的是
「`plugins/spec-guard/` 有没有变」而不是「HEAD 有没有变」——
后者会因为纯文档提交误报（0.7.2 那次自己踩过）。
0.7.3 起 hook 每轮自报 `spec-guard: v<version>`，重启后一眼可见。
